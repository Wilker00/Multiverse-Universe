# Agent Studio Workspaces

Use these rules for task composition, run inspection, memory review, execution planning, and evaluation views. Treat static implementations as interaction prototypes unless a connected service proves otherwise.

## Shell

- Lead with the current task, state, evidence, and next action rather than a generic dashboard.
- Keep no more than four frequent destinations inline on desktop. Put secondary destinations in one labeled menu.
- Use a compact menu panel on phone and tablet. Preserve every required destination and a 44px target.
- Do not add a sidebar until repeated workflows demonstrate a persistent cross-page need.

## Visual Hierarchy

- Give each primary workspace one compact orientation panel when approved artwork exists. Use it to distinguish the destination, not to imply evidence or system state.
- Pair the orientation panel with no more than one approved mascot pose in the active viewport. The mascot provides a prompt, boundary, or completion cue.
- Keep the Multiverse signature visible through the asymmetric media corner, twin-oval eyebrow signal, black mascot stage, IBM Plex typography, and pure-white canvas.
- Place operational content below the visual introduction as ruled records, controls, traces, tables, or real artifacts. Do not turn evidence into decorative image cards.
- On phone, reduce the orientation panel beside the heading rather than dropping all imagery or placing a tall card before the task.
- Avoid duplicate mascot instances inside one panel. If the artwork already contains the character, do not add an SVG overlay.

## Task Entry

- Ask for an outcome that can be checked. If no objective check exists, say that human judgment is required.
- Pair the input with one primary action. Suggestions may scroll inside their own rail, but the page must never scroll horizontally.
- Keep prototype limits near the action: scripted output does not establish capability, correctness, or learning.

## Roles and Activity

- Show role names in plain text with neutral, compact markers when identity must be scanned quickly.
- Reserve the mascot for guidance and brand moments; never clone it into agent avatars.
- Avoid colored agent cards, glowing nodes, gradient orbs, animated thinking decoration, and theatrical waveforms.
- Announce meaningful state transitions. Do not narrate every token or imply that motion proves work.

## Evidence and Memory

- Label model agreement as a combined or selected draft, never as truth or verification.
- Treat extracted memory as a candidate. Require provenance, scope, review state, and an explicit keep, verify, or reject decision before reuse.
- Display traces, metrics, and alternatives as ruled records or compact rows rather than nested card dashboards.
- Separate a simulation from a connected execution path in both language and control state.

## Responsive Contract

- At 320px, keep the task, action, status, recovery, and evidence available without page-level horizontal scrolling.
- Convert wide comparisons and tables into labeled records or hide only redundant columns; never hide the decision or result.
- Use real viewport emulation for phone validation. Desktop headless window resizing may enforce a false minimum layout width.
- Validate every destination, not only the initial task screen.

## Static Prototype Boundary

- Keep HTML, CSS, and JavaScript split into maintainable files.
- Use local fonts and repository assets; do not depend on remote font or icon requests.
- Make unavailable connected actions visibly disabled and explain the dependency in adjacent copy or the control title.
- Do not present locally generated run counts, costs, reviews, or evaluations as production telemetry.
