# Language and copy

Plain language is the default for every Multiverse interface. Technical language is allowed only when it adds necessary precision.

## Core rules

- Lead with the person's goal, decision, or next action rather than the system's internal process.
- Use familiar words, short sentences, and one main idea per sentence.
- Do not stack specialist terms when an everyday phrase communicates the same meaning.
- Define unavoidable technical terms on first use or place a plain-language explanation directly beside them.
- Expand unfamiliar acronyms on first use. Do not place unexplained acronyms in navigation, buttons, headings, or empty states.
- Keep buttons and labels action-led. Prefer "Check movement limits" over "Execute kinematic validation."
- Preserve exact formulas, units, identifiers, hardware names, and safety terms when precision matters; explain their practical meaning nearby.
- Do not make copy vague or inaccurate merely to make it simpler.

## Research and technical content

- Start each technical section with a plain-language summary of what is being tested and why it matters.
- Put the simple explanation before the formula, metric, architecture term, or implementation detail.
- Use specialist vocabulary only in the smallest region that needs it, such as a formula label, measurement row, or technical appendix.
- Explain concepts through observable actions: what the system sees, checks, changes, or prevents.
- On phone layouts, do not hide the plain-language explanation while showing only technical metadata.

## Review test

Read the interface without the formulas and metadata. A non-specialist should still understand the purpose, current state, and next action. If not, rewrite the visible copy before shipping.
